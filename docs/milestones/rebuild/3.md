# Governing architecture rule



# Strictness requirements

Assume fail-closed behavior.

The Pydantic comparison must test configurations equivalent to:

```python
ConfigDict(
    extra="forbid",
    strict=True,
)
```

Where strict mode prevents currently accepted legitimate inputs, document the exact incompatibility instead of silently enabling broad coercion.

Test potentially dangerous coercions such as:

```text
"false" → truthy/boolean ambiguity
"10.5" → Decimal/float
1 → string identifier
naive datetime → aware datetime
unknown enum value
unknown configuration field
negative amount
fractional share quantity
```

Pydantic parsing success must never be treated as business-rule approval.

# Required comparison dimensions

For each representative boundary, compare:

## Code reduction

```text
current production lines responsible for generic parsing
proposed model/conversion lines
custom validators still required
duplicate schema definitions introduced or removed
```

Do not count comments, tests, or domain rules as removable parsing code.

## Error behavior

Compare:

```text
error type
error message stability
field path
multiple-error aggregation
machine-readable error codes
whether callers currently rely on exact messages
```

## Unknown-field behavior

Verify unknown keys fail closed where the existing loader uses a closed vocabulary.

## Secret safety

Test invalid payloads containing fake secrets.

Confirm that:

```text
exceptions do not expose raw secrets unnecessarily
model repr does not expose secret values
structured logs would not receive unredacted payloads
validation metadata remains bounded
```

Use fake values only.

## Performance

Measure at least:

```text
cold import/startup cost
single-validation latency
repeated validation latency
```

Use `timeit` or another deterministic local method.

Record hardware, Python version, Pydantic version, iteration count, and methodology.

Do not overstate microbenchmark precision.

Performance matters most for:

```text
CLI startup
per-message JSONL validation
high-volume provider payloads
```

It matters less for configuration loaded once at startup.

## Dependency impact

Record:

```text
installed packages
wheel size or approximate installed footprint
import-time implications
Python compatibility
whether pydantic-core native wheels are available for supported targets
```

Use package metadata from the scratch environment.

# Decision framework

Score each boundary independently.

Use:

| Criterion | Weight |
|---|---:|
| Removes substantial generic parsing code | 20% |
| Improves fail-closed behavior | 20% |
| Improves stable/machine-readable errors | 15% |
| Preserves secret safety | 15% |
| Avoids undesirable coercion | 10% |
| Performance acceptable for invocation frequency | 10% |
| Does not duplicate domain invariants | 10% |

Do not use the score mechanically.

A boundary may still be rejected when it creates:

```text
safety ambiguity
secret leakage risk
coercion differences
duplicate domain authority
unstable public error behavior
unacceptable protocol overhead
```

   ```text

   ```
4. The ADR must explicitly supplement—not silently supersede—ADR 0001.
5. Define:
   - permitted boundary categories;
   - prohibited internal-domain usage;
   - strict-mode defaults;
   - `extra="forbid"` defaults;

   - secret handling;
   - error-contract expectations;
   - performance expectations;
   - dependency/import boundaries;
   - rollout and rollback requirements.
6. Do not mark the ADR accepted.
7. Do not add the dependency.

If no adoption is recommended, do not create a Pydantic ADR. Record the decision in `DECISIONS.md`.
