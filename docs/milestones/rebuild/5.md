## PR #9 — exchange_calendars migration

### High — Remove the moving default date bounds

Change `_calendar()` so it does not rely on:

```python
get_calendar("XNYS")
```

without explicit dates.

`exchange_calendars` defaults to a calendar beginning approximately 20 years before construction and ending approximately one year after construction. The `lru_cache(maxsize=1)` then freezes that moving window for the process lifetime.

Construct XNYS with an explicit project-supported range or use a safely cached year/range-based calendar strategy.

Preserve support for historical evaluation and future scheduling beyond the library’s default window.

Add tests covering dates outside the default range, including:

```text
a valid historical date earlier than the default 20-year window
a valid future date later than the default one-year window
next_trading_session near the configured upper boundary
add_trading_days crossing the configured upper boundary
regular_session_close for an older valid historical session
```

All public methods must either return the correct result within the documented supported range or raise a precise `MarketCalendarError`.

### Medium — Preserve accurate error classification

Narrow the exception handling in `regular_session_close()`.

Do not translate every library exception into:

```text
<date> is not a trading session
```

Differentiate:

* an actual weekend or exchange holiday;
* a date outside the configured calendar range;
* failure to construct or query XNYS;
* timezone database failure.

Wrap each case in `MarketCalendarError` while preserving the original cause.

### Medium — Add non-session horizon fixtures

Add independent tests for `add_trading_days()` when `start` is:

```text
Saturday
Sunday
exchange holiday
one-off exchange closure
early-close session
```

Verify that `start` remains day zero and that positive `n` counts only subsequent XNYS sessions.

Also test `next_trading_session()` with both `inclusive=True` and `inclusive=False` for those same categories.

### Low — Document the supported calendar range

Update the market-calendar module docstring and migration documentation to state:

```text
the exact supported historical and future range
how the range is constructed
what happens outside the range
that the implementation uses packaged offline calendar data
that future one-off emergency closures cannot be known before the library is updated
```

Do not claim arbitrary-date support unless tests prove it.
